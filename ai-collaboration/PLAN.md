# 双臂协作 + 强化学习选抓取顺序 方案

## 目标
传送带一次排 3 件，两台臂轮流抓，Q 表决定下一件先抓哪个，让两台臂尽量不空等，缩短整批完成时间。

## 背景（组长 v2 现状）
- 双臂并联分色：arm1 负责 bin_blue / bin_yellow，arm2 负责 bin_red / bin_green（bin_arm_map 固定）。
- 两臂共享唯一取件点：传送带尾部（带尾取件区）。
- 当前一次只掉一件，上一件完全完成才掉下一件；调度器单槽串行（relay_sequencer），两臂不会同时动。
- 机械臂状态可通过话题（/task/status 等）实时获取。
- 组长已同意由我们修改，改完我们自己跑。

## 框架（在组长代码上增加）
1. 掉料改动：一次掉 3 件排在带上，不再一件一件掉。
2. 取件区锁：同一时间只允许一台臂进入带尾取件区，另一台等待，防撞。
3. 状态监听节点（新增）：订阅 /task/status 等话题，实时整理两臂是否空闲、所处阶段，以及带上剩余工件及颜色。
4. RL 决策（新增）：调度器 task_dispatcher_node.py 的 _try_dispatch 中，原"按顺序派发"改为"由 Q 表选择派哪一件"。
5. 记录与分析：CSV 记录每批顺序、每件耗时、整批总时间；analysis.py 画图。

## 强化学习设计
- 状态 State：两臂各自是否空闲 + 带上剩余工件颜色组合
- 动作 Action：选择带上第几件先派发
- 奖励 Reward：放对一件 +10，失败 -10，按整批总时间扣分，臂空等扣分
- 训练：先在 Gazebo 测出每台臂抓放平均耗时，用纯 Python 简化排队模型快速训练数千轮（Gazebo 本身太慢，无法直接训练），训练后冻结 Q 表
- 验证：冻结 Q 表接入调度器，状态从真实话题实时读取，在 Gazebo 跑若干批，与"按顺序抓"对比总时间和成功率

## 分步顺序
1. 24.04 虚拟机安装 ROS2 Jazzy，跑通组长原版（双臂默认模式一轮 8 件），记录内存
2. 测量每台臂抓放耗时，写简化模型，训练 Q 表
3. 改掉料、加取件区锁、加状态监听节点、调度器接入 Q 表
4. 回 Gazebo 对比，出图，写进 HANDOFF.md

## 约束
- 不改组长原版本：在复制的副本上修改
- 不动组长的锚点标定值和判定阈值
- 单臂 ROS1 按颜色选速度的版本保留，作为保底成果
- 大模型/语音控制由组长负责，本方案不涉及


## 现行修订与离线实现契约（2026-10-15）

### 目标及边界
固定每批四色数量，Q 表仅决定下一件出料颜色。一次只推一件，最多一个送料请求/待取工件；双臂各最多一件执行中。取件区严格全局互斥，离区后的搬运、放置、返回能否与另一臂重叠，须由 Grok 验证。当前模型支持切换重叠假设，不证明实际运动安全。

现有 /move_action 共享执行槽可能阻止双臂运动重叠；不得直接移除保护。CARRYING 早于 carry_rise/carry_anchor，不能视为安全退出。推板判停必须关联本次送料工件，不能查看所有未终态工件。失败/返回失败不等于区域清空或机械臂 READY。

### 分工及目录
- Grok：Jazzy/Gazebo、原版运行、计时、task_dispatcher_node.py、relay_sequencer.py、送料逻辑、执行器事件、状态监听与互锁、真实执行重叠验证。
- Codex：ai-collaboration/codex_rl/ 下的纯 Python 模型、训练、Q 表编解码校验、两个基线、测试、使用文档。不得修改组长 ROS 包、锚点、阈值、语音功能。
- HANDOFF.md 由 Grok 写实测数据与交接；Codex 每次开工先读，审查和改动记录追加 REVIEW.md。本轮按用户要求将 Codex 交付写 REVIEW，不代写 Grok 的空 HANDOFF。

### 状态/动作 v1（离线原型，接入前双方核对）
颜色顺序固定 [blue,yellow,red,green]，路由数字 [0,0,1,1]；0=arm1，1=arm2。
动作顺序 [FEED_BLUE,FEED_YELLOW,FEED_RED,FEED_GREEN,WAIT_NEXT_EVENT]，编码 0..4。
WAIT 只能推进到一个严格未来事件，没有未来事件时不得空转。

状态 key 是紧凑 JSON 数组的字符串，固定十项：
[n_blue,n_yellow,n_red,n_green,phase_arm1,phase_arm2,eta_arm1,eta_arm2,color_arm1,color_arm2]。
remaining 表示尚未请求的需求，发请求预留时减一；不代表未完成数量。
phase 概念含 READY/PICK/POST_PICK/RECOVERY。v1 只在送料通道清空、取件区释放时决策，表中仅出现 READY/POST_PICK。PICK 期间自动推进；RECOVERY 未建模，线上必须停止策略决策、交确定性恢复逻辑。
active_color 使用 0..3，空闲为 -1。READY 必须 eta=0 且 color=-1。
ETA 使用配置的阶段时长减已过去时间估算，不能训练时偷看随机未来。
正忙时 eta=1+bisect_left(edges,剩余秒数)，edges 初值 [5,10,20]：1 为 <=5s，2 为 (5,10]s，3 为 (10,20]s，4 为 >20s。忙但估计超时仍记 1，不得当 READY。
状态例：[1,1,1,1,"POST_PICK","READY",2,0,0,-1]。
所有边界均为调度估计值，不是组长的机械判定阈值。

决策时刻：初始、确认安全离开取件区、机械臂 READY；同一时刻的事件先一起处理。
动作合法掩码独立于 Q 表：剩余需求>0、通道空、状态可靠、互锁满足。allow_prefeed_busy_arm 配置决定是否可为忙臂提前送料；默认 true 只是离线假设，真实运行待测。只有一件可等待，不能为忙臂连发。

### 模型/配置/奖励
事件链：送料请求（含后续请求延迟）→ 送料完成（到位+视觉+推板停稳的合成时长）→ 等待目标臂/互锁 → 取件 → 安全退出 → 搬运放置返回 → READY。
全部占位耗时与 ETA 边界集中在 codex_rl/config/timing.placeholder.json。所有颜色耗时当前为假设；没有失败、箱格差异、动态碰撞和共享 MoveIt 执行槽的精确模型。
allow_arm_overlap=false 为保守的机械臂全周期互斥场景，不是 MoveIt 实现的逐轨迹复刻。
批次总时间从第一次出料请求到最后一臂 READY；启动等待不计，后续请求延迟单独配置。成功计数只表示模型任务完成，不是 Gazebo 的 PLACED 判定。
奖励=-事件间隔- idle_weight×有本臂未服务需求的 READY 秒数，两臂空闲可累加。离散事件的时间间隔不固定，使用有限回合 gamma=1，避免按动作次数折扣。最后一次转移包括全部返回收尾时间。
模型第一版只模拟成功路径；失败时长/概率未有实测，不伪造失败训练。接入前必须补齐恢复定义或明确限定使用范围。

### Q 表格式及回退
schema_version=1；包含 color_order/action_order/state_fields/color_to_arm/eta_bin_edges_seconds/timing_model_version/config_sha256/is_placeholder/overlap_validated/deployment_ready/fallback_policy/q_values。
q_values 把状态 key 映射为五个有限数字；非法动作列可存在，但选择和 bootstrap 必须掩码。未知状态回退：优先 READY 臂，其次 ETA 档小的臂，同档按颜色序。配置版本/哈希不匹配、重复 JSON key、非有限数字、非法状态应拒绝整表。
占位表 deployment_ready=false，不用于直接控制 Gazebo。当前原型即使替换实测时长也不会自动宣称可部署。

### 基线和测试
原版串行基线：给定颜色顺序，上一臂完成返回后才请求下一件（抽象原版时序）。简单规则：同一批次库存和新送料/互锁机制，优先给空闲臂送料，否则按 ETA 档及颜色序。
对比三个策略必须使用同一批次颜色数量；串行使用可复现的原顺序。Q 策略与简单规则用相同重叠/预送料配置，区分流水化收益和学习收益。
测试覆盖：空批次、单件/同臂/跨臂已知时间、单取件区、单送料槽、库存守恒、忙臂等待、收尾计时、禁并发、WAIT 推进、非法动作、Q 表损坏/版本/未知状态回退、合法 bootstrap、训练可复现与保存加载。

### 等 Grok 交接
需要颜色/臂/箱格分组的原始事件时间戳，sim_time 与 monotonic_time 分列；送料、取件锁持有、离区后返回、执行槽等待、异常恢复单独记录。验证双向“取件×搬运/放置/返回”组合；确认安全退出与 READY 定义、预送料可行性。数据写入 HANDOFF 后更新配置版本，重新训练，不沿用旧表。
